## 1. 개요 및 최종 목표 (Executive Summary)

- **목표 과제**: 모션 플래닝 (Motion Planning) — Waymax 시뮬레이터 기반 폐루프(Closed-loop) 주행 궤적 생성
- **팀명/모델명**: [팀명 미기재] / V-Max SAC-LQ Planner (Hard-case Sampling A/B, Phase-3)
- **핵심 접근 전략(Key Differentiators)**:
  1. **전략적(hard-case) 데이터 샘플링 A/B 검증**: hanam 91-step 데이터 전량(35,172개)을 SDC 기준 요레이트·가속도변화·근접객체수로 스코어링한 뒤, 동일 크기(N=15,000)의 "어려운 케이스 60% + 무작위 40%" 세트와 "완전 무작위" 세트를 각각 학습시켜 나란히 비교함으로써 hard-case 마이닝 자체의 순수 효과를 분리 측정함
  2. **checkpoint-resume 기능의 실전 검증**: 2차 보고서에서 합성 테스트로만 검증했던 완전 resume 기능이, 이번 3차 실험 도중 실제로 발생한 컴퓨터 비정상 종료(재부팅) 상황에서 의도대로 동작해 데이터 손실 없이 학습을 이어감을 실증함
- **핵심 발견**: 동일한 데이터 양(N=15,000)에서는 hard-case 샘플링이 완전 무작위보다 명확히 우수했으나(`rideflux_aggregate_score` 0.506 vs 0.400), 둘 다 데이터 양이 더 많은 기존 베이스라인(hanam_run1, 전체 35,172개 무작위, 0.538)에는 못 미침 — **"어떤 데이터를 고르는가"보다 "얼마나 많은 데이터를 보는가"가 이번 실험 규모에서는 더 큰 영향력을 가짐**을 확인함

## 2. 시스템 아키텍처 및 연산량 최적화 (System Architecture)

### 2.1 전체 파이프라인 (Phase-3 신규 구성요소)

[다이어그램: hanam 91-step 전량(35,172개) → score_scenarios.py(SDC 기준 요레이트·가속도변화·근접객체수 스코어링, CSV 출력) → sample_shards.py(퍼센타일 순위 기반 hard/random 샘플 선택 + 심링크 샤딩) → {shards_hardcase(N=15,000, hard_frac=0.6), shards_random_control(N=15,000, hard_frac=0)} → jeju_run1 warm-start + SAC 학습(hanam_hardcase1 / hanam_random_control1) → evaluate.py(hanam_run1과 동일 300-샘플 평가) → 3자 비교]

| 단계 | 입력 | 처리 | 출력 |
|---|---|---|---|
| ① 스코어링 | hanam 91-step 35,172개 | `score_scenarios.py`: SDC 기준 max\|yaw_rate\|, max\|accel\|, 30m 이내 근접객체수(3개 윈도우 중 최대값) | `hanam_scores.csv` (35,172행, 실패 0, 175초) |
| ② 전략적 샘플링 | 스코어 CSV | `sample_shards.py`: 3개 지표 퍼센타일 순위 평균 → 상위 `hard_frac`만큼 hard + 나머지 무작위 fill, 심링크 샤딩 | `shards_hardcase@15000`, `shards_random_control@15000` |
| ③ 이어학습(A/B) | jeju_run1 가중치 + 각 샤드셋 | `algorithm.pretrained_params_path` warm-start + SAC 200,000 스텝 | `hanam_hardcase1`, `hanam_random_control1` |
| ④ 평가 | 각 체크포인트 + hanam_run1 평가와 동일한 300-샘플(seed=42) | `evaluate.py` (896 episode, batch_size=4, deterministic policy) | 3개 `evaluation_results.txt` |

### 2.2 score_scenarios.py 스코어링 결과 분포

hanam 91-step 파일 35,172개(파일당 3-윈도우 packing, 결과는 파일 단위 max 집계) 전량에 대한 스코어 분포:

| 지표 | p50(중앙값) | p90 | p99 | max |
|---|---|---|---|---|
| max\|yaw_rate\| (rad/s) | 0.016 | 0.052 | 0.264 | 0.391 |
| max\|accel\| (m/s²) | 1.258 | 2.065 | 3.234 | 119.228* |
| max 근접객체수(30m) | 3 | 11 | 25 | 51 |

\* accel 최대값(119.228 m/s²)은 물리적으로 비정상적인 이상치로, 센서/트래킹 노이즈에 의한 순간 튐일 가능성이 높음 — 후속 정제 필요(6장 액션아이템)

### 2.3 checkpoint-resume 기능의 실전 검증

- 2차 보고서 6.4절에서는 합성 테스트(1,280→3,200 스텝)로만 resume 기능을 검증했으나, 이번 hanam_hardcase1 학습 도중 **실제로 사용자 컴퓨터가 비정상 종료(재부팅)** 되는 사건이 발생함
- 재부팅 후 `runs/hanam_hardcase1/model/` 확인 결과 `train_state_latest.pkl`(env_steps=320 시점)이 온전히 남아있었고, **동일 명령을 그대로 재실행하자 자동으로 env_steps=320부터 복원되어 이미 완료된 구간을 재실행하지 않고 정상적으로 이어서 완주함**(로그: `-> Resuming full training state... Done (env_steps=320).` → `-> 320/200000 steps already done, 625 iterations remaining`)
- 이는 실험실 조건이 아닌 **실제 장애 상황에서의 첫 실증 사례**로, 로컬 저사양 환경(전원 불안정, OS 문제 등)이나 향후 Colab 등 세션 제한 환경에서의 안정적 운용 가능성을 뒷받침함

## 3. 데이터 처리 및 도메인 적응 (Data Engineering)

### 3.1 A/B 실험 설계

과적합·데이터양 변수를 통제하기 위해 세 조건을 다음과 같이 구성함:

| 실행명 | 데이터 소스 | 규모 | 비고 |
|---|---|---|---|
| hanam_run1 (기존, 2차 베이스라인) | hanam 전체 풀 | 35,172개 (무작위 셔플, 실제 소비량 약 2,500 시나리오) | 대조 기준 |
| hanam_hardcase1 (신규 A) | hard-case 60% + 무작위 40% | 15,000개 고정 | hard-case 마이닝 효과 측정 대상 |
| hanam_random_control1 (신규 B) | 완전 무작위 | 15,000개 고정 (동일 seed=42) | "데이터 양 축소" 변수만 남긴 대조군 |

A와 B는 데이터 양(N=15,000)과 warm-start 출발점(jeju_run1)·하이퍼파라미터가 완전히 동일하고 **오직 파일 선택 기준(hard_frac 0.6 vs 0)만** 다르므로, 두 결과의 차이는 hard-case 마이닝 자체의 순수 효과로 해석 가능함

### 3.2 도메인 적응 관련 핵심 판단 (1·2차 보고서 대비 변경 없음)

- livinglab 제외, jeju+hanam 실도로 데이터 집중 전략 유지
- **한계(1·2차와 동일)**: 평가셋(300개 샘플, seed=42)은 hanam 학습 풀에서 추출된 것으로 진성 held-out이 아님. 세 실행이 모두 같은 평가 방법론을 공유하므로 **상대 비교(A vs B vs 기존)의 유효성은 유지**되지만, 절대 점수 자체는 낙관적으로 해석해야 함

### 5.3 해석 — 두 가지 변수의 분리

1. **hard-case 마이닝 자체의 순수 효과 (A vs B, 동일 N=15,000)**: hanam_hardcase1(0.5057)이 hanam_random_control1(0.3997)을 **명확히 앞섬**(+0.106). `progress_ratio`(0.699 vs 0.531)와 `comfort`(0.737 vs 0.673) 모두 hard-case 쪽이 우세하고, `at_fault_collision`만 무작위 쪽이 근소하게 낮음(0.112 vs 0.138) — 종합적으로 **"동일한 데이터 예산이라면 어려운 케이스 위주로 학습하는 편이 유리하다"**는 가설이 지지됨
2. **데이터 양(N) 자체의 효과 (A vs 기존 hanam_run1)**: hard-case로 정교하게 고른 15,000개조차 무작위로 고른 35,172개 전체(0.5375)에는 못 미침 — 특히 `offroad_in_box`(0.013 vs 0.156)에서 격차가 큼. 이는 **더 많은 시나리오 다양성(도로 구조·상황의 폭)이 도로-경계 인식 능력에 특히 중요**하며, 15,000개로는 그 다양성이 부족했을 가능성을 시사함
3. **실무적 함의**: hard-case 샘플링을 "데이터를 줄이는 도구"가 아니라 "같은 양의 데이터 안에서 비중을 조절하는 도구"로 써야 함 — 예컨대 전체 35,172개를 그대로 쓰되 hard-case 샘플이 리플레이 버퍼에 더 자주 뽑히도록 가중치를 주는 방식(가지치기가 아닌 재가중)이 다음 단계로 유력함(6장 액션아이템)

### 5.4 위험 상황(Edge Case) 분석

- 세 실행의 `evaluation_episodes.csv`(각 896행)가 모두 확보되어 있어, 동일 300개 시나리오에 대해 세 정책이 어떻게 다르게 실패하는지(예: hard-case 모델이 특정 시나리오에서만 offroad를 내는지) episode 단위 교차분석이 가능한 상태 — 후속 작업으로 이관
