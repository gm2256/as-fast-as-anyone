> **문서 성격 안내**: 본 보고서는 `report_rule.md` 목차 지침을 따르되, 실제로 수행·측정된 결과만을 근거로 작성함. 1차 보고서(`자율주행AI기술보고서_20260905_140457.md`, jeju 단일 사이트 200,000 스텝)에서 명시한 액션 아이템 중 **"① hanam 데이터 통합"** 을 완료한 결과를 다룸. hanam 91-step 변환·샤딩을 마치고, jeju_run1 최종 정책 가중치를 warm-start로 불러와 hanam 데이터로 동일 조건(200,000 스텝) 이어학습을 수행했으며, jeju 때와 동일한 방법론의 폐루프 평가로 두 체크포인트를 직접 비교함. **전체 데이터의 극히 일부(약 2.4%)만 사용한 스모크-테스트 규모**라는 1차 보고서의 한계는 이번에도 동일하게 적용됨을 재차 명시함.

## 1. 개요 및 최종 목표 (Executive Summary)

- **목표 과제**: 모션 플래닝 (Motion Planning) — Waymax 시뮬레이터 기반 폐루프(Closed-loop) 주행 궤적 생성
- **팀명/모델명**: [팀명 미기재] / V-Max SAC-LQ Planner (Jeju→Hanam Warm-start, Phase-2)
- **대회 문제 정의**: `ScenarioScore = no_collision × on_road × (7·progress + 3·comfort) / 10` 수식으로 채점되는 폐루프 모션 플래닝 정책 학습
- **핵심 접근 전략(Key Differentiators)**:
  1. **데이터 사이트 확장**: 1차 보고서의 jeju 단일 사이트(23,753개 91-step 파일)에 **hanam 사이트(35,172개 91-step 파일)를 추가 통합**하여, 대회 test set 구성(`test_public.tar.gz` 기준 hanam 2,359 / jeju 1,965 / livinglab 0)과 정합되는 실도로 2개 사이트 커버리지를 확보함
  2. **이어학습(Warm-start Fine-tuning)**: V-Max SAC 트레이너에 이미 구현되어 있던 `algorithm.pretrained_params_path` 옵션(코드 수정 없이 즉시 사용 가능)을 활용, jeju_run1의 `model_final.pkl` 정책 가중치를 초기값으로 불러와 hanam 데이터로 이어학습 — 처음부터 재학습하지 않고 기존 학습 자산을 재사용하는 전략을 검증함
  3. **저장공간 제약 대응**: 원본(raw) 301-step TFRecord와 변환된 91-step 데이터를 동시에 보관할 디스크 여유가 없는 상황에서, **파일 단위 변환 완료 여부를 프로그램적으로 검증한 뒤에만 원본을 삭제**하는 안전한 정리 절차를 적용하여 데이터 유실 없이 약 123GB를 회수함
- **베이스라인 대비 현재 상태**: 여전히 베이스라인 권장 학습량(25,000,000 스텝) 대비 0.8% 규모(200,000 스텝)이며, 이번 실행의 의의는 "**두 사이트 데이터 통합 파이프라인이 정상 동작하고, warm-start 이어학습이 실제로 성능을 개선하는 방향으로 작동함**"을 정량적으로 확인하는 데 있음. 성능 자체의 최종 비교(전체 데이터·수백만 스텝 규모)는 아직 유효하지 않음

## 2. 시스템 아키텍처 및 연산량 최적화 (System Architecture)

### 2.1 전체 파이프라인 (Phase-2 갱신)

[다이어그램: hanam 원본 TFRecord(301-step) → make_91f.py(WOMD 91-step 변환, 원본 완전변환 검증 후 raw 삭제) → make_waymax_shards.py(hanam 35,172개 심링크 샤딩) → jeju_run1 model_final.pkl(pretrained_params_path로 로드) → V-Max SAC 이어학습 루프(hanam_run1) → evaluate.py(jeju와 동일 방법론의 폐루프 평가) → 두 체크포인트 정량 비교]

| 단계 | 입력 | 처리 | 출력 |
|---|---|---|---|
| ① 데이터 변환 | hanam 301-step TFRecord 35,172개 | `make_91f.py`: 시나리오당 3개 윈도우 절단·재포맷 (2회 세션에 걸쳐 완주, 실패 0) | 91-step TFRecord 35,172개 |
| ② 원본 정리 | 변환 완료된 raw 폴더 | 날짜별 폴더 단위로 "원본 파일 집합 ⊆ 변환 파일 집합" 검증 후에만 `shutil.rmtree` 수행 | 약 123GB 회수, 미완료 폴더는 보존(사고 방지) |
| ③ 샤딩 | 91-step TFRecord 트리 | `make_waymax_shards.py` | `train_91f_shards.tfrecord@35172` |
| ④ 이어학습 | jeju_run1 `model_final.pkl` + hanam 샤드 | `algorithm.pretrained_params_path`로 가중치 로드 후 SAC 이어학습 (JAX/XLA) | `hanam_run1/model_final.pkl` |
| ⑤ 평가 | hanam_run1 체크포인트 + 300개 샘플(seed=42) | `evaluate.py` 폐루프 롤아웃 (jeju_run1과 동일 방법론) | `evaluation_results.txt` (896 episode) |

### 2.2 Warm-start 이어학습 메커니즘

- `vmax/agents/learning/reinforcement/sac/sac_trainer.py:115-118`에 기존 구현된 로직을 그대로 활용함:
  ```python
  if pretrained_params_path:
      loaded_params = train_utils.load_params(pretrained_params_path)
      training_state = training_state.replace(params=loaded_params)
  ```
- **적용 범위 명확화**: 이 방식은 **정책/가치망 가중치만** 이어받는 warm-start이며, 옵티마이저 모멘텀·리플레이 버퍼·환경 스텝 카운터는 매 실행마다 초기화됨. 옵티마이저 상태까지 포함하는 완전한 checkpoint-resume 기능은 현재 코드베이스에 없으며, 이번 단계에서는 필요성이 낮다고 판단하여(스모크-테스트 규모 특성상) 구현을 보류함 — 향후 수백만 스텝 규모 학습을 이어갈 때 재검토 필요(6장 액션아이템)
- 네트워크 구조(encoder=lq, layer_sizes 등)가 jeju_run1과 완전히 동일한 하이퍼파라미터 조합으로 구성되어 shape mismatch 없이 가중치 로드가 성공함을 확인함

### 2.3 저장공간 제약 대응 (신규 최적화 항목)

- hanam 원본(301-step) 76GB 상당과 91-step 변환본을 동시 보관할 여유 공간이 부족해 변환 도중 디스크 고갈이 발생함
- 대응: 날짜별 폴더 단위로 `raw_files ⊆ converted_files` 여부를 파일명 집합 비교로 검증한 뒤에만 원본을 삭제하는 스크립트를 작성·실행 — 미완료 폴더 28개는 보존하고 완료된 73개(83GB) + 이후 28개(39.7GB) = 총 **약 123GB**를 안전하게 회수함
- 1차 보고서의 RAM 제약 대응(`num_envs` 축소)에 이어, **디스크 제약** 또한 로컬 6GB GPU/저사양 환경에서 실전적으로 관리해야 할 자원 제약으로 확인됨

### 3.2 도메인 적응 관련 핵심 판단 (1차 보고서 대비 변경 없음)

- 대회 공식 Motion Prediction test set 구성(hanam 2,359 / jeju 1,965 / livinglab 0)에 근거해 livinglab을 계속 제외하고 hanam·jeju(실도로) 데이터에 집중하는 전략을 유지함. 이번 hanam 통합으로 test set과 동일한 2개 사이트 커버리지를 확보함
- **한계(1차와 동일)**: 이번 hanam 평가 역시 hanam 91-step 학습 풀에서 무작위 샘플링(seed=42, 300개 파일)한 것으로, **학습에 이미 사용된 데이터와 동일 풀에서 추출한 진성 held-out이 아님**. 5장의 성능 개선 수치는 과적합 가능성을 배제하지 못하는 낙관적 추정치로 해석해야 함

- hanam 35,172개 파일 전량 변환 성공(실패 0, `sdc_invalid_windows` 0) — jeju에 이어 hanam에서도 `make_91f.py` 파이프라인의 안정성을 재확인함

## 4. AI 모델 설계 및 핵심 제어 알고리즘 (Model & Strategy)

### 4.1 보상 함수 및 하이퍼파라미터 (1차 보고서 대비 변경 없음)

- 보상 함수(`overlap: -1.0`, `offroad_in_box: -1.0`, `expert_progression: 10.0`, `termination_keys: [offroad_in_box, overlap]`)는 1차와 동일하게 유지함 — 이어학습 실험의 목적이 "데이터 사이트 확장 + warm-start 효과 검증"이므로, 보상 설계 변수를 고정해 비교 가능성을 확보함
- 하이퍼파라미터(`num_envs=4`, `buffer_size=20,000`, `learning_start=2,000`, `total_timesteps=200,000` 등) 역시 jeju_run1과 완전 동일 — 유일한 차이는 `path_dataset`(hanam 샤드)과 `algorithm.pretrained_params_path`(jeju_run1 가중치) 두 항목뿐

### 4.2 실행 명령 재현 정보

```bash
uv run vmax/scripts/training/train.py \
    algorithm=sac network/encoder=lq \
    total_timesteps=200000 num_envs=4 num_episode_per_epoch=1 \
    algorithm.buffer_size=20000 algorithm.learning_start=2000 \
    algorithm.pretrained_params_path=runs/jeju_run1/model/model_final.pkl \
    waymo_dataset=true \
    path_dataset=/home/ehdtod001009/vmax_workdir/train_91f_shards/train_91f_shards.tfrecord@35172 \
    name_run=hanam_run1 log_freq=50 save_freq=5000
```

- Hydra override 문자열에 비-ASCII 경로(한글 폴더명 "대회")가 포함되면 `LexerNoViableAltException`이 발생함을 확인 — `pretrained_params_path`는 절대경로 대신 **작업 디렉터리 기준 상대경로**로 지정하여 우회함(재현 시 유의사항으로 기록)

- 참고로 200,000 스텝 기준, `num_envs=4 × scenario_length=80`으로 실제 소비되는 시나리오 수는 약 2,500개 수준으로, hanam 전체 샤드(35,172개, 시나리오 약 105,516개)의 **약 2.4%만 랜덤 샘플링**되었음 — 전체 데이터를 활용한 학습이 아님을 명확히 함

### 5.2 폐루프 평가 결과 비교 (evaluate.py, `--sdc_actor=ai`, 동일 방법론)

- **평가 데이터**: 각 실행의 학습 풀에서 무작위 추출한 300개 91-step 파일(seed=42) → `make_91f.py`의 파일당 3-윈도우 패킹 구조로 인해 실제로는 약 896 episode로 전개됨(300×3=900에서 SDC 경로 무효 케이스 약 4개 제외) — jeju/hanam 두 평가 모두 동일한 로직으로 재현됨
- **평가 소요**: jeju 896 episode/99.57초, hanam 896 episode/97.75초 (둘 다 batch_size=4)

| 지표 | jeju_run1 | hanam_run1 | 대회 채점식 대응 관계 |
|---|---|---|---|
| accuracy | 0.6317 | **0.7455** | — |
| at_fault_collision | 0.1931 | **0.1295** | no_collision 항의 반대급부(↓좋음) |
| offroad_in_box | 0.1138 | **0.0134** | on_road 항의 반대급부(↓좋음) |
| progress_ratio | 0.6350 | 0.6302 | progress 항 직접 대응 |
| comfort | 0.6008 | 0.6895 | comfort 항 직접 대응 |
| min_ttc / average_ttc | 3.634 / 4.700 | 4.364 / 4.891 | 안전 여유 시간 |
| nuplan_aggregate_score | 0.1051 | **0.1826** | 참고용 |
| vmax_aggregate_score | 0.0938 | **0.1607** | 참고용 |
| **rideflux_aggregate_score** | 0.4417 | **0.5375** | **대회 ScenarioScore와 가장 근접** |

- **해석**: warm-start 이어학습 이후 대회 채점식과 가장 근접한 `rideflux_aggregate_score`가 0.44→0.54로 상승했고, 특히 채점식의 이진(0/1) 곱셈 항에 해당하는 `offroad_in_box`(0.114→0.013)와 `at_fault_collision`(0.193→0.130)이 큰 폭으로 개선되어 "0점 처리되는 시나리오 비율"이 실질적으로 줄었을 가능성이 높음
- **주의**: 3.2절에서 명시한 대로 이 평가는 진성 held-out이 아니며, 두 실행 모두 스모크-테스트 규모(200k step)이므로 이 개선폭이 (a) hanam 데이터 특성이 jeju보다 학습하기 쉬운 분포였을 가능성, (b) warm-start로 인한 실질적 전이학습 효과, (c) 우연적 변동 중 무엇에 기인하는지는 현재 실험 설계로 분리할 수 없음 — 진성 held-out 검증셋 구축(6장 액션아이템) 이후 재확인 필요

### 5.3 위험 상황(Edge Case) 분석

- 1차와 동일하게 본 단계에서는 시나리오 유형별 세분화 분석을 수행하지 않음. `evaluation_episodes.csv`(jeju/hanam 각 896행)가 양쪽 모두 확보되어 있어, 두 사이트 간 실패 패턴 차이(예: hanam에서 `offroad_in_box=1`인 케이스의 도로 구조적 특징) 비교 분석이 후속 작업으로 가능함

- 기존 `pretrained_params_path`(가중치만 이어받는 cross-run warm-start)는 그대로 유지하고, 같은 run을 이어받는 `resume`과 역할을 분리함
- **실증 검증**: 1,280 스텝 학습 후 종료 → 동일 `name_run`으로 목표치를 3,200으로 늘려 재실행 → 로그에 `env_steps=1600`부터 정확히 이어받아 이미 완료된 구간을 재실행하지 않고 남은 6 iteration만 처리 후 정상 종료함을 확인. Colab 등 세션 시간 제한 환경에서 안전하게 학습을 이어갈 수 있는 전제 조건을 충족함

**(2) 전략적(hard-case) 데이터 샘플링 스크립트 구현 및 전체 스코어링 완료**
- `scripts/score_scenarios.py`: hanam 91-step 파일(35,172개) 전량에 대해 SDC 기준 최대 요레이트·최대 가속도 변화·최대 근접 객체 수(30m 이내)를 계산해 CSV로 저장 — 35,172/35,172 성공, 에러 0, 175초 소요
- `scripts/sample_shards.py`: 위 스코어를 퍼센타일 순위로 정규화해 상위 hard_frac 비율만큼은 난이도 상위 파일에서, 나머지는 무작위로 채워 새 학습 샤드셋을 구성하는 도구. 소규모 테스트로 동작 검증 완료
- **아직 실제 학습에는 미적용** — 다음 단계로 N=15,000, hard_frac=0.6 규모의 hard-case 샘플셋과 동일 규모의 순수 무작위 샘플셋을 나란히 학습·비교하는 A/B 실험이 대기 중

**(3) hanam_run1 베이스라인 확정 시도 — jeju 회귀 검증 불가**
- hanam_run1이 jeju_run1 가중치를 이어받아 hanam만 보며 학습했다는 점(4.2절, 2.2절)에서, 이는 jeju+hanam을 함께 본 "결합 학습"이 아니라 **순차적 전이학습**이며, hanam 전용 학습 단계에서 jeju 주행 패턴을 잊었을(catastrophic forgetting) 가능성을 배제할 수 없음을 재확인함
- 이를 검증하기 위해 hanam_run1 체크포인트로 jeju 평가셋을 재평가하려 했으나, **jeju 원본·91-step 변환 데이터가 디스크에 전혀 남아있지 않아(디스크 공간 확보 과정에서 삭제된 것으로 추정) 재평가가 불가능함**을 확인함. 외장 저장소·마운트된 드라이브에서도 발견되지 않음
- **결정**: 위 한계를 명시적으로 인지한 상태로, **hanam_run1을 잠정(provisional) 베이스라인으로 채택**함. jeju 회귀 여부는 "미확인 리스크"로 남겨두며, jeju 원본을 재확보하는 즉시 최우선으로 재평가할 것
